IBM Z DATATHON 2026  |  UPDATED CONCEPT DOCUMENTATION
LogMind
A security analyst AI that cannot be hijacked by the logs it reads
Draft v2  |  15 October 2026  |  Primary track: AI Secured: Innovation Without Exposure  |  Secondary track: Real-Time AI for Critical Decisions
Core principle: Logs are untrusted evidence. Rules decide; AI explains.
1. The idea at a glance
In simple words
In technical terms
You upload a small log file. LogMind checks it for common private details, looks for a suspicious pattern, hides any text an attacker could have planted, and asks an AI to explain the evidence. The analyst can see the original record and exactly what the AI was allowed to read.
The updated demo adds two things: a safe log-upload check and a visible attack replay. They show what was removed before the AI was called, what the AI received, and whether its explanation is supported by the records. LogMind is a helper for analysts. It is not a complete SIEM, a website scanner or an automatic response tool.
LogMind is a small SIEM-style prototype that detects one account-compromise sequence and uses AI to explain it. A prototype pipeline accepts supported authentication and web-server text logs, runs a file preflight, normalizes events, applies deterministic correlation, pseudonymizes identifiers, quarantines attacker-controllable fields, calls a pluggable read-only LLM, validates the structured output and displays evidence-linked results.
Fixed rules determine the alert and its severity. The updated demo adds an upload data guard and an Attack Replay, and exposes the removed content, the model input and the validation result. Scope: an analyst aid, not a SIEM, website scanner or automated response tool.
2. The problem we are solving
Aspect
In simple words
In technical terms
What goes wrong
Security teams get more records than a person can read one by one. AI can help summarize suspicious activity, but some of the text in those records is written by outsiders, such as the browser name or the web address in a request. An attacker can plant a fake instruction there, and an AI that reads the raw text may treat it as an order.
Some log fields hold values an outsider controls, for example a browser User-Agent or a URL. If the model reads the raw text, it may treat the attacker’s words as directions. This is prompt injection hidden in the evidence being analyzed.
Privacy exposure from uploads
Uploading a log file creates a second risk. The file may contain names, email addresses, IP addresses, session tokens or other secrets. So the file should be checked before anything is sent to an AI. We are honest that a simple check will not catch every private value.
A log file may contain names, email addresses, IP addresses, session tokens or other secrets. A prototype should check supported uploads before any content reaches a model, while stating plainly that simple pattern checks will not detect every sensitive value.
3. The solution: five design principles
LogMind does not promise that the AI cannot be fooled. It limits how much the AI can influence, and it checks the upload before processing begins.
Aspect
In simple words
In technical terms
1. Rules decide; AI explains
A fixed if-then rule decides that something is an attack and how serious it is. The AI only writes the explanation. It cannot lower the alert and it cannot trigger any response.
Deterministic rule sets the verdict and severity. Model output can write an explanation but cannot lower the alert or trigger a response; the validator enforces a severity floor.
2. Check before processing
Before anything is analyzed, the uploaded file is checked. Only supported plain-text log formats are accepted. The check looks at file type and size, flags common private details and secret-looking strings, and shows a preview before analysis starts.
Only supported text log formats are accepted. The upload guard checks file type and size, flags common identifiers and secret-like strings, and shows a preview before analysis.
3. Keep attacker text away from the AI
Anything an outsider could have typed is swapped for a label such as [UA#14]. The AI sees the label, not the words. The original stays available to the analyst inside the protected application.
Field quarantine: attacker-controllable fields are replaced by opaque tokens such as [UA#14]. The original is retained inside the protected application.
4. Minimize personal data
Real names and IP addresses become consistent aliases where possible. Obvious secrets are masked, or the upload is stopped for review.
Pseudonymization with consistent aliases where possible; obvious secrets are masked, or the upload is rejected for review.
5. Verify and show evidence
The AI cannot take any action. Its answer must follow a fixed format and point to real record numbers. A separate checker, which is ordinary code and not an AI, verifies the answer before the analyst sees it.
The model has no tools or write access. Output must follow a schema and cite event IDs. A plain-code validator checks structure and references before display.

Core LogMind workflow
Aspect
In simple words
In technical terms
Sample log import
You can upload a small log file, but only certain kinds: plain text, CSV or JSON, below a size limit. The first version handles login logs and web-server logs only.
Accept only documented plain-text, CSV or JSON files within a size limit. The first build supports authentication and web-server events only.
Upload Data Guard
Before analysis, LogMind scans the file for things that look like email addresses, IP addresses and passwords or tokens. It shows what would be hidden, and the user chooses to mask those values and continue, or to reject the file. Office documents and programs are not accepted.
Flag common email, IP and credential/token-like patterns; show a redaction preview; let the user mask and continue or reject the file. Arbitrary binary and office-document files are not accepted in the prototype.
Rule-based detection
A fixed rule looks for the attack pattern: several failed logins, then a success, then a high-level action, all by the same account.
Identify repeated failed logins followed by a success and a privileged action for the same pseudonymized account.
Field quarantine and pseudonymization
The AI is given safe facts and labels instead of the attacker’s actual words or real identities.
Pass safe features and opaque tokens to the model instead of raw attacker-controlled values.
Evidence-linked explanation
Every important statement the AI makes points to a specific record. Clicking it opens that record in the dashboard.
Every key claim cites event IDs that open the relevant record in the dashboard.
Output validation
A checker rejects an AI answer that is badly formed, points to records that do not exist, gets counts or times wrong, or rates the alert lower than the rule did. If that happens, a plain summary written by the rules is shown instead.
Reject malformed output, unknown event IDs, unsupported counts or timestamps, and severity below the rule verdict. If validation fails, show a rule-generated summary.

10. Honest limitations and decisions to confirm
Not injection-proof. The design limits the AI’s influence; it cannot guarantee that every generated sentence is correct.
The upload guard is a small preflight. It is not a complete data-loss-prevention or malware-scanning product. It only handles declared text log types and common detectable patterns.
Narrow detection coverage. One attack sequence, two event sources and synthetic data. It can miss different attacker behavior and may flag benign sequences.
Quarantine loses context. The AI cannot interpret the hidden raw value; the analyst must use the original evidence when that detail matters.
The output validator has limits. It can check schemas, IDs and fixed constraints, but it cannot fully prove the meaning of free-form text. Keep claims structured and evidence-linked.
Platform features unconfirmed. Local model hosting, Secure Execution, confidential containers and Telum acceleration are not assumed. Confirm availability and quotas with IBM before relying on them.
No website scanning or attacking. If a later version includes active testing, restrict it to an isolated lab target or a system with explicit authorization.
11. Glossary
Term
Meaning
SIEM
Security information and event management: a system that collects logs, detects suspicious activity and helps analysts investigate.
Prompt injection
An instruction hidden in content that an AI is asked to read, intended to change the AI’s behavior.
Attacker-controlled field
A log value that an outsider can influence, such as a User-Agent, URL or attempted username.
Quarantine
Replace attacker-controlled text with a token before giving structured event data to the AI.
Pseudonymization
Replace real identities with consistent aliases so events can still be linked.
Evidence link
A reference from an explanation claim to a source event ID.
Severity floor
A rule that prevents an AI-generated explanation from lowering the rule-based severity.
Data guard
A limited upload check that flags common sensitive patterns and previews or masks them before analysis.
